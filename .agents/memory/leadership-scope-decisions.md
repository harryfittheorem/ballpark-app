Build native CRM; do not retain GoHighLevel as the CRM backend. Fully leave Mindbody; do not design a permanent Mindbody software dependency.

**Why:** The creator explicitly chose these directions during requirements review; existing integrations or prototype terminology must not reverse them.

**How to apply:** Distinguish native CRM from SMS/voice/email delivery infrastructure. Treat historical data import and payment-method portability as different problems.

Use manual performance entry now while API access is investigated. This settles input method, not whether distance is retained alongside exit velocity.

**Why:** The creator confirmed manual entry while API feasibility remains open.

**How to apply:** Do not make API access a launch prerequisite or delete historical measurements. Preserve dated measurements and source provenance.

Compare native Tap to Pay with secure online card entry/payment links before selecting GM-phone payment approach. Extending existing role-based mobile screens is a recommendation, not approved packaging.

**Why:** The creator requested a payment comparison and staff-mobile recommendation without selecting either approach.

**How to apply:** Do not assume a tapped card is reusable for recurring charges. Leadership review is documentation-only, not authorization for software changes, provider selection or external actions.
